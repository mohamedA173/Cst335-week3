# Integrity and Trade-Off Reflection

In the relational design, the database handles a lot of the integrity stuff for you. Because of the foreign keys, you can't add a note or a visit for a student that doesn't exist, and you can't delete a student who still has notes connected to them. NOT NULL and the data types also make sure things like dates and emails are actually filled in. So if something is wrong, the database just won't save it.

MongoDB is more flexible, but that makes it easier to end up with messy data. There's no set schema, so if one document says "serviceType" and another says "service_type," MongoDB will take both. A student could also be missing the supportVisits array completely, which would break my count query if I didn't use $ifNull. If I had put visits in their own collection, a visit could still point to a student who got deleted. This connects to what we learned about CAP in Week 3, where NoSQL databases usually give up some consistency so they can be more flexible and scale easier.

To protect integrity in MongoDB, I added a $jsonSchema validation rule to my students collection. It makes studentId, email, and the dates on notes and visits required, and it only allows certain values for category and serviceType. I also added unique indexes on studentId and email so there can't be duplicate students. I tested it by trying to add a visit with "gym" as the service type and MongoDB rejected it. The app should still check data before saving it too, and running a cleanup script every once in a while would help catch anything that slips through. MongoDB can do all of this, you just have to set it up yourself since it doesn't happen automatically like it does with SQL.
